## AWS to Cloudflare Migration Completion Plan

Based on thorough analysis of the codebase and migration documentation, here is the plan to complete the migration of all AWS resources to Cloudflare equivalents:

### Phase 1: Remove AWS SDK Dependencies (PR-14)
**Target:** Complete the uninstall of all AWS SDK clients as outlined in the migration documentation

**Files to modify:**
- `package.json`: Remove these dependencies:
  - "@aws-sdk/client-bedrock-runtime": "^3.1104.0"
  - "@aws-sdk/client-cost-explorer": "^3.1104.0"
  - "@aws-sdk/client-dynamodb": "^3.1104.0"
  - "@aws-sdk/client-sesv2": "^3.1104.0"
  - "@aws-sdk/client-ssm": "^3.1104.0"
  - "@aws-sdk/client-iam": "3.1104.0" (devDependency)

**Verification:** Run `rg '@aws-sdk' package.json src/` to confirm empty after removal

### Phase 2: Clean Environment Configuration
**Target:** Remove AWS credentials and configure Cloudflare equivalents

**Files to modify:**
- `.env.example`: 
  - Remove/comment out AWS sections:
    - AWS_REGION, AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY
    - SSM_PREFIX (if no longer using SSM)
    - Cognito variables (if auth is fully D1-only)
    - SES variables (if using Cloudflare Email Service/Resend only)
  - Add/retain Cloudflare variables:
    - CLOUDFLARE_ACCOUNT_ID
    - CLOUDFLARE_API_TOKEN
    - CLOUDFLARE_EMAIL_API_TOKEN (if using Cloudflare Email Service)

### Phase 3: Address Remaining AWS Usage in Code
**Target:** Replace actual AWS SDK usage with Cloudflare equivalents

**Files to update based on findings:**

1. **Bedrock Runtime replacement** (`/scripts/generate-product-descriptions.ts`):
   - Replace BedrockRuntimeClient with Workers AI REST API calls
   - Use existing `src/lib/workers-ai-client.ts` or `src/lib/workers-ai-chat.ts`

2. **DynamoDB Client replacement**:
   - **Replication subscriber** (`/infrastructure/r20-replication/subscriber.ts`):
     - Replace DynamoDB writes with D1 operations using existing D1 helpers
     - Consider if this Lambda can be replaced with Cloudflare Workers or if R2 can store replication data
   - **Migration script** (`/scripts/archive/aws-sdk-migration/migrate-dynamodb-to-d1.ts`):
     - This is an archive script - verify if still needed or can be removed after migration completion

3. **SSM Client replacement**:
   - **SES SMTP provisioning** (`/scripts/archive/aws-sdk-migration/provision-ses-smtp.ts`):
     - Replace SSM Parameter Store with D1 app_config table or Wrangler secrets
     - Use existing `src/lib/ssm-config-d1.ts` patterns
   - **Secret sync script** (`/scripts/archive/aws-sdk-migration/sync-ssm-to-wrangler.ts`):
     - Verify if still needed after SSM deprecation

4. **IAM Client replacement** (same file as SES SMTP provisioning):
   - Replace IAM user/access key management with Cloudflare equivalent approach
   - Consider if SMTP credentials can be managed via Cloudflare Email Service directly

### Phase 4: Verify Cloudflare Equivalents
**Target:** Ensure all Cloudflare replacements are functioning correctly

**Verification steps:**
- Confirm Workers AI is being used for AI/ML tasks (replacing Bedrock)
- Confirm D1 is being used for data storage (replacing DynamoDB)
- Confirm Cloudflare Email Service/Resend is being used for email (replacing SES)
- Confirm R2 bindings/aws4fetch are being used for object storage (replacing S3)
- Confirm D1 app_config + Wrangler secrets are being used for configuration (replacing SSM)

### Phase 5: Run Cleanup and Validation
**Target:** Validate the migration and clean up remnants

**Steps:**
1. Run `pnpm install` to update dependencies
2. Run `pnpm test` to ensure unit tests pass
3. Run `pnpm test:e2e:smoke` to verify basic functionality
4. Consider running the cleanup script: `scripts/cleanup-migrated-aws-resources.sh` (after verifying backups)
5. Deploy changes using SST/OpenNext workflow

### Migration Wave Context
This plan focuses on completing:
- **Wave C:** PR-14 (Uninstall all @aws-sdk/* dependencies)
- **Preparation for Wave D:** PR-16 (Decommission AWS resources) and PR-17 (Drop Cost Explorer ETL)

The core application is already running on Cloudflare infrastructure as evidenced by:
- SST configuration showing AWS resources as deprecated
- Auth using D1 provider (`NEXT_PUBLIC_AUTH_PROVIDER=d1`)
- Multiple Cloudflare equivalents implemented and in use
- Migration documentation showing most waves as completed

Immediate focus on removing AWS SDK dependencies will allow progression to full AWS account teardown.
